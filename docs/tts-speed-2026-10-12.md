# 本地连续朗读模型选择：实机基准

日期：2026-10-12。测试目的：解决当前本地语音克隆模型生成慢的问题；先测试再替换。本轮没有改插件默认服务、用户选择或发布插件。

## 选择

**默认本地朗读候选：Kokoro v1.1-zh 原精度 FP32，通过 Sherpa-ONNX，CPU 4 线程。** 选择依据是用户同时需要连续朗读、换中文音色和中英阅读，不能只选合成时间最低的一项。官方映射提供 100 个中文、3 个英文音色，模型标注 Apache 2.0。实际测试了女声 `zf_001`（sid 3）和男声 `zm_009`（sid 58），并非全部 103 个音色都验收。正常表现可跟上播放，但其中一次男声连续句测试出现两次慢请求；需要更多预取余量，不能仅凭中位数承诺无停顿。量化 INT8 版不作为当前 Mac 默认。

**纯中文、速度优先的备选：MeloTTS 中文/英文转换模型，通过同一个 Sherpa-ONNX 引擎，CPU 4 线程。** 它在两次完整测试中都有较充足的速度余量、较低的内存占用，模型包附 MIT 许可。但该模型只有一个音色，不提供语音克隆；官方说明英文仅能读词典中的词。本次核对词典包含 `Obsidian` / `machine` / `learning`，不含 `OpenAI` / `IndexTTS2` / `Sherpa` / `ONNX` / `Kokoro`。不能因通用中英混读测试生成了音频就承诺任意英文专名均可读。需要补充词典或其他读法处理，因此不作为满足全部需求的唯一默认。没有对任一候选宣称主观音质最好。

**Piper 华严不作为本次默认分发候选。** 它最省时，但下载包内 `MODEL_CARD` 对训练数据许可标为 `Unknown`；需进一步核对这个具体音色模型的使用条件。引擎的开源许可不能直接替代声音模型的许可。

F5 / Spark / IndexTTS2 继续视为高级语音克隆候选；已完成安装或短句生成不代表满足即时朗读。F5 本轮实测速度明显不够；Spark 未完成同口径速度基准，Index 的真实播放器试听曾超时，均不应默认推荐为实时朗读模型。

## 实测环境与口径

- Apple M5 Pro，48 GiB，macOS 27.0.1；CPU 推理，未使用 CUDA、MPS 或 CoreML。
- 独立 Python 3.11.11；`sherpa-onnx` / `sherpa-onnx-core` 1.13.8，NumPy 2.4.6，SoundFile 0.13.1。
- 所有权重与测试环境在 `~/Library/Application Support/qiaomu-reader/tts/benchmarks/sherpa-1.13.8/`，不在 vault 或插件目录。合成只读本地模型，没有云端合成调用。
- 新进程加载后，先生成一次短句，再生成三次相同短句，以三次中位数作为热身后延迟。速度固定为 1.0；不同模型的自然语速不同，所以同时记录音频时长。
- 四线程完整测试包括短句、约百字段落、数字日期、中英混读、连续四句，共 11 次合成。Melo / Kokoro 女声另各复测一次完整序列；Kokoro 男声完整测试一次。
- 依赖导入、模型初始化与首句全量合成之和作为新进程首次等待，不含首次安装、下载、OS 进程启动；没有清空磁盘缓存，不等同于重启后冷机测试。
- 这是正常使用中的电脑，未关闭用户其他应用。Kokoro 男声尾延迟出现后，观察到其他应用正在使用 CPU，但没有足够证据确定延迟原因。模型基准按顺序运行；最初另一个有并发推理的 Melo 单线程记录不参与推荐。

## 同一句中文的完整合成

文本：`阅读让我们看见更大的世界，也理解不同的人生。`

| 模型 / 路径 | 热身后完整生成 | 音频时长 | 生成耗时 / 音频时长 | 新进程首次全量等待 |
| --- | ---: | ---: | ---: | ---: |
| MeloTTS / Sherpa CPU 4 线程 | 1.03 秒；复测 1.14 秒 | 约 3.92 秒 | 0.26；复测 0.29 | 2.21；复测 2.51 秒 |
| Kokoro FP32 女声 / Sherpa CPU 4 线程 | 1.72 秒；复测 1.67 秒 | 约 4.63 秒 | 0.37；复测 0.36 | 2.53 秒 |
| Kokoro FP32 男声 / Sherpa CPU 4 线程 | 1.72 秒 | 约 4.68 秒 | 0.37 | 2.64 秒 |
| Piper 华严 / Sherpa CPU 4 线程 | 0.15 秒 | 约 3.97 秒 | 0.037 | 1.01 秒 |
| F5-TTS / 现有 MPS 路径，两个参考音色 | 11.55 / 13.47 秒 | 4.36 / 4.83 秒 | 2.65 / 2.79 | 未同口径测量 |

比值小于 1 表示这次生成速度超过正常播放消耗速度；不保证任意输入、电脑负载和倍速都能连续播放。

## 长段与连续播放限制

| 模型 | 整段生成 | 音频时长 | 第一批内部 PCM 输出 |
| --- | ---: | ---: | ---: |
| Melo 4 线程 | 4.35 秒；复测 4.60 秒 | 16.52 秒 | 0.18 秒 |
| Kokoro FP32 女声 4 线程 | 7.42 秒 | 20.07 秒 | 0.32 秒 |
| Kokoro FP32 男声 4 线程 | 7.92 秒 | 20.52 秒 | 0.40 秒 |
| Piper 华严 4 线程 | 0.68 秒 | 16.08 秒 | 0.10 秒 |

内部回调提供了按句输出能力，但这些时间**不是插件已经开始播放的时间**。现有 `TtsController` 仍等待整段音频后才播放，只预取下一段。要实际改善体验，需要按句输出/切片、维持可播放队列，预取按音频秒数管理，同时保留原段落的进度锚点。

Melo 两次完整序列中，最大生成耗时/音频时长约 0.30。Kokoro 女声两次序列最大约 0.44；男声一次序列中的最后两句用 9.65 / 7.53 秒生成 5.82 / 6.15 秒音频。这些慢请求保留在原始数据中，未当作异常值删除。它们没有出现无效波形，但可能耗尽播放队列；原因尚未确定。

对这组连续四句，按现有仅提前一段的策略计算，Melo 正常和 2 倍速均有余量；Kokoro 女声在 2 倍速的一次过渡预计缺约 0.20 秒。这是依据实际耗时的计算，**不是实际播放器无间断验收**，任意长短交替段落仍可能等待。

### Kokoro 线程与精度

| CPU 线程 | FP32 女声短句生成中位数 | 耗时/音频时长 |
| --- | ---: | ---: |
| 1 | 4.45 秒 | 0.96 |
| 2 | 2.59 秒 | 0.56 |
| 4 | 1.72 秒 | 0.37 |
| 8 | 1.74 秒 | 0.38 |

8 线程长段约 6.04 秒，较 4 线程快，但短句没有明显改善，因此本机优先取 4 线程。不能将这组线程设置直接推定为所有 Windows / 手机设备的最佳参数。

INT8 版短句生成约 3.2–3.6 秒，长段没通过非空、有限、非静音波形校验，初始失败日志未区分具体校验条件。不能因为下载包更小就认为它在 Apple Silicon 更快或更可靠；本轮保留失败记录并排除它。

## 复现

使用已安装的私有测试环境运行 [基准脚本](../scripts/bench-local-tts.py)。脚本不会安装依赖或下载模型，不读取书籍、密钥或用户设置。

```sh
python scripts/bench-local-tts.py \
  --root '/path/to/benchmarks/sherpa-1.13.8' \
  --output /tmp/tts-benchmark \
  --engine melo --threads 4

python scripts/bench-local-tts.py \
  --root '/path/to/benchmarks/sherpa-1.13.8' \
  --output /tmp/tts-benchmark \
  --engine kokoro --kokoro-precision fp32 --sid 3 --threads 4
```

Sherpa 官方播放例子的回调返回 `1` 继续、`0` 停止。本轮发现 Python 接口的文字注释与官方播放例子存在歧义；最初返回 `0` 导致仅合成第一批片段的结果已排除，报告数据均返回 `1` 并包含完整段落。

本次来源为官方 GitHub 发布的固定资源名；四个实际下载的 SHA256 均记录在原始数据。两个 Kokoro 包有发布方 SHA256，并已匹配；Melo / Piper 发布资源没有提供 digest，记录的是本次下载计算所得哈希，不宣称验证了发布方签名。
